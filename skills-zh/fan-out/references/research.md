# fan-out：调研

派发调研类 fan-out 之前先读这一篇。调研是 fan-out 最对口的场景——信息空间大过一个上下文，而且各个角度之间本来就不需要互相通气。

**角度必须是真的不同。**默认按来源类型切，因为不同来源的失真方式不一样：

- 官方材料——文档、规格、changelog、东西本身的源码
- 社区与前人实践——issue、讨论、博文、竞品实现，以及人们放弃某条路线的理由
- 论文与形式化论述，如果这个话题有的话
- 真实世界里的代码——真实仓库到底是怎么用的，这一条经常和文档打架

来源类型切不开这个问题时，改按子系统切、按时间窗切（两个版本之前是什么样、现在是什么样——凡是变动频繁的话题都少不了这一刀），或按立场切（拥护者、怀疑者、运维者）。检验一个切法的办法：问自己两个 agent 会不会带回同一批链接。会，那就是一个 agent 的活。

**每个 explorer 先广后精。**写进契约里：先把这片空间扫一遍、汇报地形长什么样，再挑最吃重的两三项往下钻。直接被瞄准一个窄问题派出去的 agent，会拿回它找到的第一个看似成立的答案然后停下——四个自信的 agent、零覆盖，就是这么来的。

**要的是可引用的原始发现，不是摘要。**每条发现带上：主张、来源名称、URL 或文件路径、话题会变动时还要带日期或版本，凡是精确的东西（数字、API 签名、承诺的保证）附原文引用。有两条禁令值得明写进契约：不做跨来源的综合（explorer 看不见别的 explorer，所以「各方说法一致」纯属猜测），不把推断包装成发现——可以推断，但要标明这是 agent 自己的推断。

**要驱动决策的东西才验证。**任何将要被决策拿来当支点的主张，都单独过一轮，这一轮的任务是证伪它、或者证明它已经过时——重开来源、核对版本、找有没有撤回或更新的说法。每条关键主张标成「已确认 / 大概成立 / 已证伪」，并写清什么情况会翻转这个结论。只是有趣但不承重的主张不配占用这份预算。

**综合时把那条线露出来。**一份报告：先给答案，再给证据，最后给未决问题。读者可能据以行动的每一句话，要么带引文、要么明显是你自己的判断——两者绝不能糊成同一种口吻。写明覆盖范围：覆盖了哪些角度、丢掉了哪些角度、哪里来源稀薄或彼此矛盾。来源之间的矛盾本身就是一个发现，如实报告，不要取个平均把它抹平。

一条边界说明：如果是扎根于项目持久上下文体系的深度调研——先读已有 contexts、把问题收紧到真正的知识缺口、验证后的结果再写回去——面向用户的入口是 `/ctx-research`，它在这套模式外面包了一层「接地」和「落盘」。本篇保持通用，不重复那套流程。
