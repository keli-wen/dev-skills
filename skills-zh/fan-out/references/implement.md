# fan-out：实现

派发写代码的 fan-out 之前先读这一篇。SKILL.md 里的关卡依然先过一遍——实现类工作的耦合度通常比看上去高，这里拆错的代价是重写，不只是浪费一个 agent。

**拆之前先摸清完整工作清单。**永远不要凭估计给 fan-out 定规模。grep、读、把每一处要改的地方都列出来，数一遍，自己看一眼这张清单。没做发现就定规模的 fan-out，要么漏掉几处没人改，要么把同一个文件派给两个 agent。如果「发现」本身就是一件大工程，那就先为它单独做一次 fan-out——explorer 各自返回清单，你合并，实现阶段从合并后的清单派发，绝不从某一个 explorer 的切片派发。

**跨切片的决策在派发前定死。**接口、函数签名、数据结构、命名、错误处理、整体方案取向都归你，趁你还握着全局的时候定下来，然后**原样**写进每一份受影响的契约。一个被告知「在这里加个缓存」的 agent 会自己发明一套 cache key 格式；三个 agent 会发明三套。任何你事后不得不去统一的东西，现在写进契约里的一句话，都比五个 agent 产出之后再重构便宜。

**沿耦合度拆，不沿工作阶段拆。**好的切法：一个 agent 负责一个调用点、一个包、一个适配层，彼此只共享你已经定死的那个接口。坏的切法：一个写代码、一个写测试、一个写文档——那恰好切在共享上下文最多的地方，每个阶段都得重新还原上一个阶段的意图。如果两个切片为了保持一致必须在执行中途互相通气，它们本来就是一个切片，合并掉。

**多个 agent 并行改同一个仓库时做工作区隔离。**共用一个 checkout 的 agent 会在索引、构建产物、彼此写了一半的编辑上互相踩，而踩出来的故障看起来像逻辑 bug。给每个要写的 agent 一个独立 git worktree、各走各的分支，最后由你来合。平台给不了 worktree，就把写操作串行化，把并行留给读。

**除标准契约字段外，每一份实现契约还要带上：**

- 定死的决策，原文照抄，不要转述
- 这个 agent 拥有的具体文件，以及绝不许碰的文件
- 用可观察行为写的验收标准，且写成验证者之后会拿到的那个形态
- 这个切片怎么构建、怎么跑测试，好让失败以结果的形式回来，而不是到整合时才冒出来
- 一条停止规则：如果发现这个切片需要改动共享接口，报告，不要自己改

**验证默认开启。**派一个黑盒验证 subagent，它只拿到验收标准和产出物——不给方案、不给实现者的推理过程、不给 diff 附带的理由说明。正是上下文会让验证者跟实现者站到一边，所以「不给」才是这件事的全部要点。只有用户明确表示不要时才跳过验证；那是进阶用户的选择，用户这么选的时候你说明一次。绝不为了省一次派发而悄悄省掉。

**整合就是排查不一致。**自己读每个 agent 的产出，专门找那种「各自正确、合起来出错」的东西：同一个标识符两种拼法、同一个 helper 被写了两遍、对空值或顺序的假设互不兼容、某个接口偏离了你定死的那版。然后对合并后的整棵树做构建和测试，而不是各切片各测各的。汇报哪些地方改了、哪些地方是有意跳过的、为什么。
