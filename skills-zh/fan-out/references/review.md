# fan-out：review

派发做代码 review 的 fan-out 之前先读这一篇。review 特别适合拆，因为各个维度之间是真正独立的：每个找问题的 agent 要的是同一份代码，和一个不同的问题。

**按维度拆，一个维度一个 finder。**四个默认维度：

- **正确性**——代码是否真在做它声称的事：逻辑、边界情况、错误与重试路径、并发、资源生命周期，以及那些看起来在测其实什么都没测的测试
- **规范**——是否遵循**这个仓库**的约定，既包括写下来的（lint 与格式化配置、CONTRIBUTING、CLAUDE.md / AGENTS.md、ADR），也包括看出来的（隔壁模块本来是怎么写的）。要求 finder 在下判断之前先从仓库里把约定确立出来，并且引用确立它的那个文件——引不出出处的约定只是个人偏好，不是问题
- **规格对齐**——是否做了发起它的 issue、工单或 spec 真正要求的事：没满足的需求、被悄悄丢掉的情况、作者自己加上去的范围
- **安全**——不可信输入抵达危险汇点、鉴权缺失或做在错误的层、密钥与日志、注入、不安全的默认值

规范和规格对齐这两个维度改编自 [mattpocock/skills](https://github.com/mattpocock/skills) 的 `code-review`（MIT）。

改动本身值得的时候再加维度——性能、迁移与向后兼容、公开 API 面、可运维性。只有在这份 diff 显然完全不涉及某个面时才砍掉那个维度，并且在报告里写明砍了。

**给每个 finder 同一份代码、不同的问题。**输入按引用给：base ref、变更路径、发起的 issue。每个 finder 返回条目化的发现，不要成段的散文：位置写成 `file:line`、错在哪、为什么在这里是错的、建议的严重级别，以及证据——引用的代码、援引的约定、没满足的那条需求。禁止跨维度评论；finder 看不见别的 finder，也不该去猜。

**然后每一条发现配一个对抗式验证者。**验证者的任务是把这条发现杀掉，不是确认它——review 稳定地会产出一批「看着很有道理但其实是错的」的发现。它只拿到发现和代码，不给 finder 的置信度和推理。它复现问题、读周边代码，逐个试那些显而易见的反驳：那个「缺失」的检查其实在上游做了、这个分支根本走不到、那条约定已经被新的取代、那条需求在别处满足了。它返回「确认 / 无法复现 / 已证伪」并附理由。只有确认的发现进报告，其余丢弃；如果一条严重的发现落在「无法复现」，值得留一句话说明。

**整合成一份按严重级别排序的报告。**跨维度的重复项合并成一条，并列出所有命中它的维度——三个 finder 各自独立撞上的问题，通常就是清单上最重要的那一条。按「阻塞 / 应修 / 小瑕疵」排序，小瑕疵写短。一个真问题一条，由你来写。绝不把 agent 的输出原样堆着交上去。

**写明覆盖范围。**review 了什么（ref、路径、文件数），以及没 review 什么：生成的文件、vendored 依赖、你砍掉的维度和原因、大到读不完的东西。不许静默截断——没说出口的缺口，读者会当成一切正常。
